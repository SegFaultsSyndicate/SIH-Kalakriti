# Multi-Language i18n Support

**Last Updated:** 2026-08-28  
**Status:** Production-ready

---

## Overview

Simple message localization for error messages and user-facing strings. Hindi and English supported. Locale extracted from `Accept-Language` header.

**Features:**
- Context-based locale storage
- Middleware for automatic locale detection
- Translatable error keys
- Fallback to English when translation missing
- ~40 common error messages pre-translated

---

## Usage

### Basic Translation

```go
import "github.com/ZoroNewbie00/kalakriti/pkg/i18n"

// Get locale from context
locale := i18n.GetLocale(ctx)

// Translate message key
msg := i18n.T(locale, "order.quantity_positive")
// English: "quantity must be positive"
// Hindi: "मात्रा सकारात्मक होनी चाहिए"
```

### HTTP Middleware

```go
import (
    "github.com/ZoroNewbie00/kalakriti/pkg/i18n"
    "net/http"
)

func main() {
    mux := http.NewServeMux()
    
    // Add i18n middleware (extracts Accept-Language header)
    handler := i18n.Middleware(mux)
    
    http.ListenAndServe(":8080", handler)
}
```

**Request with Hindi:**
```bash
curl -H "Accept-Language: hi" http://localhost:8080/api/orders
```

**Request with English (default):**
```bash
curl http://localhost:8080/api/orders
```

### Error Messages

**Without translation:**
```go
// Old way (hardcoded English)
if quantity <= 0 {
    return domain.InvalidInput("quantity must be positive")
}
```

**With translation:**
```go
// New way (translatable key)
if quantity <= 0 {
    return domain.InvalidInput(i18n.T(i18n.GetLocale(ctx), "order.quantity_positive"))
}
```

**HTTP response with Hindi locale:**
```json
{
  "error": "मात्रा सकारात्मक होनी चाहिए"
}
```

### Adding New Locale

```go
// pkg/i18n/i18n.go

const (
    English Locale = "en"
    Hindi   Locale = "hi"
    Marathi Locale = "mr"  // New locale
)

var marathiMessages = map[string]string{
    "err.not_found": "सापडले नाही",
    "order.quantity_positive": "प्रमाण धनात्मक असावे",
    // ... more translations
}

func T(locale Locale, key string) string {
    if locale == Marathi {
        if msg, ok := marathiMessages[key]; ok {
            return msg
        }
    }
    if locale == Hindi {
        if msg, ok := hindiMessages[key]; ok {
            return msg
        }
    }
    return englishMessages[key]
}
```

## Accept-Language Header

### Header Format

```
Accept-Language: hi,en;q=0.9,en-US;q=0.8
```

**Parsing logic:**
1. Split by comma
2. Check if any language starts with `hi` → Hindi
3. Otherwise → English

**Examples:**
- `hi` → Hindi
- `hi-IN` → Hindi
- `en` → English
- `en-US` → English
- `hi,en;q=0.9` → Hindi (first preference)
- (empty) → English (default)

### Browser Language Detection

Modern browsers automatically send `Accept-Language` based on user's language preferences.

**Chrome:** Settings → Languages → Preferred languages  
**Firefox:** Preferences → Language → Choose languages  
**Safari:** Uses system language

## Example: Service Layer

```go
package service

import (
    "context"
    "github.com/ZoroNewbie00/kalakriti/pkg/domain"
    "github.com/ZoroNewbie00/kalakriti/pkg/i18n"
)

type OrderService struct {
    // ...
}

func (s *OrderService) CreateOrder(ctx context.Context, in CreateOrderInput) (Order, error) {
    locale := i18n.GetLocale(ctx)

    if in.Quantity <= 0 {
        return Order{}, domain.InvalidInput(i18n.T(locale, "order.quantity_positive"))
    }

    if in.BuyerID.IsNil() {
        return Order{}, domain.InvalidInput(i18n.T(locale, "order.buyer_required"))
    }

    // ... create order
}
```

**API Response (Hindi):**
```bash
$ curl -X POST http://localhost:8080/api/orders \
  -H "Accept-Language: hi" \
  -H "Content-Type: application/json" \
  -d '{"quantity": 0, "buyer_id": "..."}'

{
  "error": "मात्रा सकारात्मक होनी चाहिए"
}
```

func handleCreateOrder(w http.ResponseWriter, r *http.Request) {
    // Locale already in context (from middleware)

}

var hindiMessages = map[string]string{

if in.Price <= 0 {

## Migration Strategy

**Current state:** Most error messages hardcoded English strings.

**Migration path:**
1. ✅ i18n infrastructure added (context, middleware, translation maps)
2. New code: Use `i18n.T(locale, key)` for all user-facing errors
3. Existing code: Migrate incrementally when touching that code (no mass refactor needed)
4. Search terms in logs/monitoring stay English (only user-facing messages translated)

**Priority for migration:**
1. Auth errors (user-facing during login/OTP)
2. Order validation errors (most common user interaction)
3. Payment errors (high-value errors)
4. Internal service errors (low priority, mostly for developers)

## Performance

**Translation lookup:** O(1) map lookup, <1μs overhead per error

**Memory:** ~5KB per language (40 messages × ~100 bytes)

**HTTP overhead:** Parse `Accept-Language` header once per request, store in context

**No impact:** Translation only happens on error path (not hot path)

---

## Limitations

**Current scope:**
- Error messages only (not UI text, emails, or notifications)
- 2 languages (English + Hindi)
- Static strings only (no pluralization, no date/number formatting)

**Not included:**
- Template rendering (emails, notifications)
- Frontend localization (React i18n, etc.)
- Right-to-left languages
- Gender-specific translations
- Plural forms (1 item vs 2 items)

**Future extensions:**
- Add `i18n.Tf(locale, key, args...)` for parameterized messages
- Load translations from JSON files (not embedded maps)
- Add more Indian languages (Marathi, Tamil, Bengali)
- Integrate with notification service for localized emails/SMS
