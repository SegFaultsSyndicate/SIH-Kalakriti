# Multi-Language i18n Support

**Status:** Infrastructure built, not wired into any response path

---

## Current reality (verified against code, not the original design doc)

`pkg/i18n` (locale parsing, `Middleware`, `T`) and `pkg/domain/i18n.go`
(`TKey`/`TKeyf`, a translatable-error type) both exist and are correctly
implemented in isolation. `i18n.Middleware` **is** mounted on the bff
(`services/bff/internal/bff/server.go:81`,
`r.Use(httpx.Wrap(i18n.Middleware))`), so a locale is parsed from
`Accept-Language` and stored in the request context on every call.

But nothing downstream ever reads it:
```
$ grep -rn "i18n\.T(\|i18n\.GetLocale(" --include="*.go" .
pkg/domain/i18n.go:17:// Use with i18n.T(locale, key) to get localized message.   <- a comment, not a call
```
`i18n.T` and `i18n.GetLocale` are called nowhere in real service or handler
code, `domain.TKey`/`domain.TKeyf` are called nowhere either, and
`pkg/domain/http.go`'s `WriteHTTPError` (the function that actually writes
every JSON error response) does `message := err.Error()` — it never
consults the request's locale or looks up a translation. **Sending
`Accept-Language: hi` today changes nothing about any API response.** The
examples below (`i18n.T(locale, "order.quantity_positive")` returning Hindi
text over HTTP) describe the intended design, not current behavior.

To make any of this real, a call site (e.g. the quantity check inside the
order service) needs to change from `domain.InvalidInput("quantity must be
positive")` to `domain.InvalidInput(i18n.T(i18n.GetLocale(ctx), "order.quantity_positive"))`
— and the doc's own message-key table below is a reasonable starting point
for which keys already exist to use.

## Overview

Simple message localization for error messages and user-facing strings. Hindi and English supported. Locale extracted from `Accept-Language` header.

**Features:**
- Context-based locale storage
- Middleware for automatic locale detection
- Translatable error keys
- Fallback to English when translation missing
- ~40 common error messages pre-translated

## Usage

### Basic Translation

```go
import "github.com/ZoroNewbie00/kalakriti/pkg/i18n"

// Get locale from context
locale := i18n.GetLocale(ctx)

// Translate message key
msg := i18n.T(locale, "order.quantity_positive")
// English: "quantity must be positive"
// Hindi: "मात्रा सकारात्मक होनी चाहिए"
```

### HTTP Middleware

Already wired into the real bff -- `services/bff/internal/bff/server.go:81`:
```go
r.Use(httpx.Wrap(i18n.Middleware))
```
(the generic `http.NewServeMux()` + `i18n.Middleware(mux)` shape below is
just how the middleware composes in isolation, not a second place it needs
adding):
```go
import (
    "github.com/ZoroNewbie00/kalakriti/pkg/i18n"
    "net/http"
)

func main() {
    mux := http.NewServeMux()
    handler := i18n.Middleware(mux)
    http.ListenAndServe(":8080", handler)
}
```

**Request with Hindi** (locale is parsed and stored in context -- but see
"Current reality" above: no response is actually translated yet):
```bash
curl -H "Accept-Language: hi" http://localhost:8000/api/v1/listings
```

### Error Messages

**Without translation:**
```go
// Old way (hardcoded English)
if quantity <= 0 {
    return domain.InvalidInput("quantity must be positive")
}
```

**With translation (not yet done at any real call site -- see "Current
reality" above; this is the change that would need making):**
```go
// New way (translatable key)
if quantity <= 0 {
    return domain.InvalidInput(i18n.T(i18n.GetLocale(ctx), "order.quantity_positive"))
}
```

**HTTP response this would produce, once wired** (today it still returns the
English message regardless of `Accept-Language` -- the real error envelope
also has a stable `error` code alongside `message`, see `docs/API.md`):
```json
{
  "error": "invalid_input",
  "message": "मात्रा सकारात्मक होनी चाहिए"
}
```

### Adding New Locale

```go
// pkg/i18n/i18n.go

const (
    English Locale = "en"
    Hindi   Locale = "hi"
    Marathi Locale = "mr"  // New locale
)

var marathiMessages = map[string]string{
    "err.not_found": "सापडले नाही",
    "order.quantity_positive": "प्रमाण धनात्मक असावे",
    // ... more translations
}

func T(locale Locale, key string) string {
    if locale == Marathi {
        if msg, ok := marathiMessages[key]; ok {
            return msg
        }
    }
    if locale == Hindi {
        if msg, ok := hindiMessages[key]; ok {
            return msg
        }
    }
    return englishMessages[key]
}
```

## Accept-Language Header

### Header Format

```
Accept-Language: hi,en;q=0.9,en-US;q=0.8
```

**Parsing logic:**
1. Split by comma
2. Check if any language starts with `hi` → Hindi
3. Otherwise → English

**Examples:**
- `hi` → Hindi
- `hi-IN` → Hindi
- `en` → English
- `en-US` → English
- `hi,en;q=0.9` → Hindi (first preference)
- (empty) → English (default)

### Browser Language Detection

Modern browsers automatically send `Accept-Language` based on user's language preferences.

**Chrome:** Settings → Languages → Preferred languages  
**Firefox:** Preferences → Language → Choose languages  
**Safari:** Uses system language

## Example: Service Layer

```go
package service

import (
    "context"
    "github.com/ZoroNewbie00/kalakriti/pkg/domain"
    "github.com/ZoroNewbie00/kalakriti/pkg/i18n"
)

type OrderService struct {
    // ...
}

func (s *OrderService) CreateOrder(ctx context.Context, in CreateOrderInput) (Order, error) {
    locale := i18n.GetLocale(ctx)

    if in.Quantity <= 0 {
        return Order{}, domain.InvalidInput(i18n.T(locale, "order.quantity_positive"))
    }

    if in.BuyerID.IsNil() {
        return Order{}, domain.InvalidInput(i18n.T(locale, "order.buyer_required"))
    }

    // ... create order
}
```

**API Response (Hindi), once the call site above actually exists** (real
port `:8000`, real route is `POST /api/v1/orders/bulk` -- see `docs/API.md`;
`buyer_id`/`quantity` aren't the real bulk-order body shape either, this is
illustrating the i18n mechanism only):
```bash
$ curl -X POST http://localhost:8000/api/v1/orders/bulk \
  -H "Accept-Language: hi" \
  -H "Content-Type: application/json" \
  -d '{"quantity": 0, "buyer_id": "..."}'

{
  "error": "invalid_input",
  "message": "मात्रा सकारात्मक होनी चाहिए"
}
```

## Example: BFF Integration

The real `services/bff/internal/bff/server.go` doesn't look like this (it
builds a gin router via `httpx.Mux`, and route registration lives in
`mountRoutes`, not `main.go`, with no bare `/api/orders` route -- see
`docs/API.md` for the actual route table). This is a minimal illustration of
the same wiring shape, not a literal excerpt:

```go
import (
    "github.com/ZoroNewbie00/kalakriti/pkg/httpx"
    "github.com/ZoroNewbie00/kalakriti/pkg/i18n"
    "github.com/gin-gonic/gin"
)

func main() {
    r := gin.New()

    // Add i18n middleware (before route handlers) -- the real bff already
    // does this, at services/bff/internal/bff/server.go:81
    r.Use(httpx.Wrap(i18n.Middleware))

    // Routes...
    r.POST("/api/orders", httpx.WrapHandler(handleCreateOrder))

    http.ListenAndServe(":8080", r)
}

func handleCreateOrder(w http.ResponseWriter, r *http.Request) {
    // Locale already in context (from middleware)
    locale := i18n.GetLocale(r.Context())

    order, err := orderService.CreateOrder(r.Context(), input)
    if err != nil {
        // Error message will be in user's language
        httpx.Error(w, err)
        return
    }

    httpx.JSON(w, 200, order)
}
```

```go
var hindiMessages = map[string]string{
```

```go
if in.Price <= 0 {
```

**If Hindi translation missing:** Falls back to English automatically.

## Migration Strategy

**Current state:** Most error messages hardcoded English strings.

**Migration path:**
1. ✅ i18n infrastructure added (context, middleware, translation maps)
2. New code: Use `i18n.T(locale, key)` for all user-facing errors
3. Existing code: Migrate incrementally when touching that code (no mass refactor needed)
4. Search terms in logs/monitoring stay English (only user-facing messages translated)

**Priority for migration:**
1. Auth errors (user-facing during login/OTP)
2. Order validation errors (most common user interaction)
3. Payment errors (high-value errors)
4. Internal service errors (low priority, mostly for developers)

---

## Performance

**Translation lookup:** O(1) map lookup, <1μs overhead per error

**Memory:** ~5KB per language (40 messages × ~100 bytes)

**HTTP overhead:** Parse `Accept-Language` header once per request, store in context

**No impact:** Translation only happens on error path (not hot path)

---

## Limitations

**Current scope:**
- Error messages only (not UI text, emails, or notifications)
- 2 languages (English + Hindi)
- Static strings only (no pluralization, no date/number formatting)

**Not included:**
- Template rendering (emails, notifications)
- Frontend localization (React i18n, etc.)
- Right-to-left languages
- Gender-specific translations
- Plural forms (1 item vs 2 items)

**Future extensions:**
- Add `i18n.Tf(locale, key, args...)` for parameterized messages
- Load translations from JSON files (not embedded maps)
- Add more Indian languages (Marathi, Tamil, Bengali)
- Integrate with notification service for localized emails/SMS

## Summary

**Setup:** `i18n.Middleware` is already mounted on the bff router
(`server.go:81`) -- locale detection works today.
**Usage:** `i18n.T(i18n.GetLocale(ctx), "error.key")` -- defined and correct,
but currently called from nowhere in the codebase.
**Coverage:** ~37 English messages, ~21 Hindi translations (see
`pkg/i18n/i18n.go` for the exact current maps).
**Fallback:** Missing translations → English
**Performance:** <1μs overhead, only on error path -- moot until something
calls it

**Next steps (current, not historical):**
1. Pick one call site (e.g. the bulk-order quantity check) and change it
   from a hardcoded English string to `i18n.T(i18n.GetLocale(ctx), "order.quantity_positive")`
   to prove the whole path end-to-end.
2. Migrate high-priority error messages (auth, orders, payments) the same way.
3. Expand Hindi coverage based on user feedback.
4. Add Marathi/Tamil when regional users request it.
